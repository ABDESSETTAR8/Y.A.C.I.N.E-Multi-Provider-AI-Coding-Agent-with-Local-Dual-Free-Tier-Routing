Static & dynamic audit — Y.A.C.I.N.E coder agent

Defect Ledger

Twenty-three defects across the security layer, the autonomous loop, and the local model transport. The three at the top let arbitrary code reach the host; the next group is why runs quietly go wrong.

Critical — the containment story does not hold

The README and the module docstrings describe a permission-gated, workspace-confined agent. Three defects mean none of that confinement actually exists at runtime.

C-01 Critical Reproduced core/security.py:73–86
tools/sandbox.py:118
tools/filesystem.py (all)

Every file tool writes anywhere on the disk

Each tool builds its target as self.sandbox.workspace / path. In pathlib, joining an absolute path discards the left side — so write_file("/etc/cron.d/x", …) resolves to /etc/cron.d/x, not to a file inside the workspace. Relative ../../ escapes work too. SecurityEnforcer.check_path() is the only gate and it never compares the resolved path against the workspace root; its traversal branch is literally a comment followed by pass.

I confirmed both escapes against a live sandbox — an absolute write and a ../../ write both returned [OK] and landed outside the workspace, and read_file("/etc/hostname") returned host contents.

Fix: one choke point. Resolve with (workspace / path).resolve(), reject unless workspace.resolve() is among its parents, reject absolute inputs and symlinks outright, and route every tool through it — list_dir and search_code currently perform no check at all.

C-02 Critical api/server.py:36–62
api/server.py:426–462

The local API is unauthenticated and open to every website

CORS is allow_origins=["*"] with allow_credentials=True, and API_KEY is sourced from _settings.model.api_key — the LLM provider's key. The documented YACINE_API_KEY environment variable is never read anywhere in the codebase, so in the default local-Ollama setup the key is empty and _check_auth() returns immediately on every request.

That leaves /run, /orchestrate, /api/upload and /api/browse reachable from any page the user has open in a browser while the server runs. /api/browse enumerates any directory on the machine; /run starts an agent that executes shell commands. Separately, /health, /models, /context/summary, /memory and the /ws event stream call no auth check at all — the WebSocket broadcasts every reasoning step, tool call and file path to whoever connects.

Fix: read YACINE_API_KEY, generate a random token on first boot if unset, and require it on all routes including the WebSocket. Pin CORS to the UI's own origin, and validate the Host header to block DNS rebinding. Use secrets.compare_digest for the comparison.

C-03 Critical tools/git.py:33–58

Shell injection through git tool arguments

Model-supplied args is interpolated straight into a command string that Sandbox.run() executes with shell=True: cmd = f'git commit -m "{msg}"'. A commit message containing a double quote closes the string and everything after it runs as shell. The same pattern applies to add, branch, checkout, tag and push.

This matters more than usual here because the argument originates from an LLM that reads untrusted input — repository files, and web pages fetched by the research agent. A prompt-injection payload in a README becomes host command execution. DANGEROUS_PATTERNS catches none of it.

Fix: drop the string entirely. Build an argv list per operation and call subprocess.run(list, shell=False). Give Sandbox.run() a list-accepting path and use it for every tool that composes a command from model output.

High — crashes, false greens, and a starved model

Two of these are unconditional NameErrors. The rest are the reasons a local coder agent appears to work and then doesn't: it declares victory without running anything, and it feeds the model more context than the model is configured to accept.

H-01 High Reproduced api/server.py:569

JSONResponse is undefined in the upload handler

The except branch of /api/upload returns JSONResponse(...), but the name is never imported in server.py. Any upload failure — a permission error, a bad multipart body — turns a clean 400 into an unhandled NameError and a 500 with a stack trace. The GUI's Upload button has no working error path.

Fix: from fastapi.responses import JSONResponse at module level.

H-02 High Reproduced orchestrator/multi_agent.py:117

tempfile is undefined on the orchestrator's default path

When workspace_root is not supplied, the constructor falls back to Path(tempfile.gettempdir()) / self._task_id — and tempfile is not imported in the module. Constructing a MultiAgentOrchestrator without an explicit workspace raises NameError before any work begins. Every UI path that omits a project folder hits this.

Fix: add the import. The same file also imports Sandbox at module level and re-imports it inside __init__; keep one.

H-03 High core/engine.py:333–343
core/engine.py:411–415

The loop reports "verified complete" without running anything

When _infer_verify_command() detects no test framework, the engine falls back to _files_exist_check(request) — which ignores its request argument entirely and returns True if the workspace contains any file at all. The coder agent writes one file, the check passes, and run() sets success=True with the verdict "Task verified complete: the implementation was built, executed, verified, reviewed, quality-checked, documented, and committed."

Nothing was executed and nothing was verified. This is the single most damaging defect in the product's core claim, because it is silent: the user is told the task passed. The method's own comment concedes it is "crude" and "a fallback only", but the return value is treated as a real green.

Fix: make an unverifiable task a distinct third outcome — success=False with a verdict that says no verification was possible. Never let a file-existence heuristic produce the same result as a passing test run.

H-04 High models/ollama.py:83–95, 120–135

Ollama is never told the context size, so long prompts are silently cut

The options block sets only temperature and num_predict. Without num_ctx, Ollama applies its default window — 4096 tokens on current builds, 2048 on older ones — and silently drops whatever overflows from the front of the conversation. Meanwhile the engine feeds it a full context block, a plan, and accumulated tool output.

The visible symptom is a model that "ignores instructions", forgets the file it just read, or re-creates work — usually blamed on the model's quality. It is a missing parameter. Paired with H-05 it is the most common practical failure mode of this system.

Fix: add num_ctx to the options, expose it in ModelConfig, and default it to the model's real window. Log prompt_eval_count against it so truncation becomes visible rather than silent.

H-05 High agents/agent.py:287–341

The agent transcript grows without bound and without loop detection

Across up to fourteen tool iterations, every raw tool result is appended to messages and none is ever trimmed. read_file returns whole files; search_code returns up to 200 matching lines; the terminal returns full stdout and stderr. Nothing summarises, truncates, or drops older turns.

There is also no repetition guard: an agent that calls the same tool with the same failing arguments will do so until max_tool_iters is exhausted, burning the whole budget on one mistake.

Fix: cap each tool result before it enters the transcript (head+tail with a middle elision), keep a rolling window of recent turns with the system prompt and task pinned, and short-circuit when the last N calls are identical.

H-06 High Reproduced core/engine.py:398–408
tools/terminal.py:63–72

Verification hardcodes python instead of the running interpreter

_infer_verify_command() returns the literal string "python -m pytest -q", and PythonExecTool hardcodes python plus a Windows-only venv/Scripts/python.exe path with a .replace("/", "\\") that also mangles any argument containing a slash. Nothing uses sys.executable.

This is what makes two of the three failing tests fail: the subprocess resolves a system python that has no pytest, the verify step reports exit 1, and the self-heal loop burns its whole budget trying to fix code that was never broken. On Linux and macOS, where python often does not exist at all, the loop can never go green.

Fix: use sys.executable (or the workspace venv's interpreter, detected per platform) everywhere a Python process is spawned, and pass it through to the sandbox rather than relying on PATH.

H-07 High tools/code_edit.py:38–58

edit_file does not check that old_string is unique

The docstring promises "unique single replacement", but the non-replace_all branch takes text.index(old_string) and edits the first hit without ever counting occurrences. When a debugger agent targets a snippet that appears in several places — a common import line, a repeated return None — it silently modifies the wrong one and reports success. The self-heal loop then re-runs the same failing test and concludes the fix didn't work.

The backup is single-slot as well: .bak is overwritten on every edit, so the second edit to a file destroys the only copy of the original, and undo_edit can rewind exactly one step.

Fix: count matches and return an error asking for more surrounding context when the count is not 1. Keep timestamped backups, or write edits through git so undo is real.

H-08 High tools/sandbox.py:71–75

Agent-generated code inherits the full host environment

run_env = dict(os.environ) hands every subprocess the complete environment of the parent process — including YACINE_MODEL_API_KEY, YACINE_TELEGRAM_TOKEN, cloud credentials, SSH agent sockets, and anything else in the user's shell. The code being executed was written moments earlier by a language model acting on untrusted repository content.

The surrounding docstring claims isolation via "a dedicated workspace directory". In practice the only real controls are a timeout and an RLIMIT_AS ceiling on POSIX; there is no user, namespace, network, or filesystem isolation, and on Windows even the memory cap is absent.

Fix: build a minimal allowlisted environment (PATH, HOME, TMPDIR, locale) instead of copying os.environ. Then either soften the "sandbox" language in the docs or back it with a real container.

H-09 High agents/agent.py:318
models/ollama.py:17–25

Tool results are sent without the assistant turn that requested them

After a tool call the loop appends Message(role="assistant", content=resp.text) — dropping the tool_calls field — then appends a role="tool" message. _to_ollama_messages() likewise carries no tool_calls through. The resulting transcript has orphaned tool results.

Ollama tolerates this; OpenAI-compatible backends reject it with a 400 ("messages with role 'tool' must be a response to a preceding message with tool_calls"), so the openai_compat provider cannot complete a multi-turn tool run. Even on Ollama, the model loses the record of what it asked for.

Fix: carry tool_calls on the assistant Message and serialise it in both provider adapters, matching each tool result to its tool_call_id.

Medium — correctness, hygiene, and honesty of the docs

Not exploitable on their own, but several of these are what turn a small failure into a confusing one.

M-01 Medium core/security.py:19–31, 47–58

The permission model is on-by-default and the blocklist is cosmetic

read_file, write_file, execute_command, delete_file and internet_access all default to True; only git_push is off. So "every sensitive action is gated" means, out of the box, that every gate is open. interactive_prompt() — the escape hatch that would ask the user — is a stub that always returns False and is never called.

DANGEROUS_PATTERNS is a regex blocklist, which is the wrong shape for this job: rm -rf ~, rm -rf ./*, rm -fr /, extra spaces, and any $(…) or base64 indirection all pass. A blocklist here gives the user confidence the system cannot back up.

Fix: default the destructive permissions off and wire a real approval callback. Keep the pattern list as a warning signal, not as the boundary — the boundary should be the path confinement from C-01 and argv-based execution from C-03.

M-02 Medium tools/filesystem.py:33, 106, 141
tools/code_edit.py:38
tools/registry.py:56

Tools construct a fresh SecurityEnforcer() and discard the configured one

make_sandbox() carefully builds an enforcer from the active settings and injects it into the Sandbox. The file tools then ignore self.sandbox.security and instantiate SecurityEnforcer() inline, which re-reads the global settings singleton. Any per-task or per-session permission tightening is silently bypassed.

Fix: always use self.sandbox.security. Remove the inline constructions.

M-03 Medium tools/internet.py:32–47

No SSRF guard on http_request

The tool fetches any URL the model produces, with redirects followed. Nothing blocks 127.0.0.1, 169.254.169.254, or private ranges — so the agent can reach its own unauthenticated API (C-02), the Ollama admin endpoints, a cloud metadata service, or anything else on the user's LAN. Content fetched this way is fed straight back into the prompt, which is also the delivery path for prompt injection into C-03.

Fix: resolve the host before connecting, reject loopback/link-local/private/reserved addresses, re-check after each redirect, and cap the response size.

M-04 Medium core/config.py:189–201

Secrets are written back to settings.yaml in plaintext

save_config() serialises the entire settings model, so an api_key or a Telegram bot_token supplied through the environment is persisted into the YAML file on the next save. The TelegramConfig docstring states the token "stays in config / env, never logged" — but the round-trip means an env-only secret becomes a file-resident one, and /api/telegram/test mutates the live global config object with a token from an HTTP request body.

Fix: exclude secret fields from save_config, resolve them from the environment at use time, and stop mutating the shared settings singleton inside a request handler.

M-05 Medium memory/store.py:104–113

The memory store rewrites the whole file on every append, unlocked

_save() opens the file in "w" mode and re-serialises every memory on each add() — quadratic as the store grows. There is no file lock and no atomic replace, while the API server handles requests on a thread pool and the engine writes memories from worker threads. A crash or a concurrent write during the truncate window loses the entire store.

Fix: append a single JSONL line for a new memory, and for full rewrites write to a temp file and os.replace it. Guard with a lock.

M-06 Medium core/engine.py:128–141

Edits to a real project never make it back to the project

run(project_path=…) copies the user's tree into a per-task sandbox with _sync_into_sandbox(), works there, and commits there. There is no reverse sync and no diff handed back. A user who points the agent at their repository gets a green result, a commit inside a temp workspace, and an unchanged repository — with the changes discoverable only by digging into workspace/tasks/<id>/.

The copy loop also has no size ceiling, no symlink guard, and swallows every per-file failure with a bare except: pass, so a partial copy looks identical to a complete one.

Fix: decide the model explicitly — either work in a git worktree of the real repo and hand back a branch, or produce a patch the user applies. Either way, surface it in TaskResult.

M-07 Medium core/config.py:212–219

The settings singleton ignores config_path after the first call

get_settings(config_path) only honours its argument when _CONFIG is None. Because api/server.py calls get_settings() at import time, every later request for a specific config file silently returns the default one — including AutonomousEngine(config_path=…), whose parameter therefore does nothing in the server process.

Fix: cache per resolved path, or reload when the requested path differs from the cached one.

M-08 Medium core/engine.py:64–76

_parse_exit guesses when it should not have to

The fallback branch treats any output containing the substring "Error" as failure and requires the literal "OK" for success. A passing test suite that prints the word "Error" in a log line reads as failed; a silent successful command with no "OK" also reads as failed. The exit code is available and authoritative — ToolResult.data["returncode"] is right there and unused at the call site.

Fix: branch on exec_res.data["returncode"] and timed_out; delete the text heuristic.

M-09 Medium tests/test_engine.py:233

The third failing test depends on ambient git identity

test_context_git_history_and_style creates a repo, commits, and asserts the message appears in the log — but the commit is made in a try/except: pass block, so on a machine without user.email configured the commit never happens, is_git_repo() is still true, and the assertion fails. The test passes or fails based on the developer's global git config rather than on the code.

Fix: pass -c user.name=… -c user.email=… to the test's git invocations and assert the commit succeeded instead of swallowing the failure.

M-10 Medium across yacine/ (82 handlers)

Failures are swallowed at a rate that makes debugging guesswork

There are 82 broad except Exception handlers, 24 of which do nothing but pass. Several sit on load-bearing paths: MCP server loading in registry.py, the per-file copy in _sync_into_sandbox, embedder selection in longterm.py, and event emission in both the engine and the orchestrator. When the agent behaves oddly there is no trace of the swallowed cause anywhere.

Fix: log at debug with the exception at minimum, and narrow the caught types where the expected failure is known.

M-11 Medium pyflakes, 60 hits
tools/filesystem.py:172
core/engine.py:472
plugins/loader.py:64

Dead code and small textual damage

pyflakes reports about sixty findings beyond the two NameErrors: unused imports in nearly every module, assigned-and-never-used locals in cli.py (settings, twice; pmod; pdoc) and telegram.py (chat_id), and f-strings with no placeholders in context.py:224 and db.py:191.

Two more worth a pass while you're in there: SearchCodeTool's 200-hit cap breaks only the inner line loop, so it keeps reading every remaining file for nothing; and plugins/loader.py carries the mangled docstring fragment "a warning isMessage delivered" — the fingerprint of an earlier find-and-replace that overwrote a word, which is exactly the failure mode H-07 describes.

Fix: run ruff --fix across the package — the project already ships a quality module that shells out to ruff, so it can be pointed at itself.

Suggested order: C-01 through C-03 first — they are small, local changes that restore the boundary the rest of the design assumes. Then H-01 and H-02, which are one-line imports. Then H-03, H-04 and H-06 together: those three are what stand between the loop and a run you can trust.

Method: pyflakes and compileall across yacine/, tests/, plugins/, scripts/; the full pytest suite under a clean venv with the pinned requirements; manual read of the security, sandbox, tool, engine, orchestrator, API and provider modules; and targeted probes against a live Sandbox to confirm the path-escape and interpreter findings. Probe artifacts were removed afterward.
